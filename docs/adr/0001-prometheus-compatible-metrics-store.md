# ADR 0001: Use VictoriaMetrics single-node for Argus telemetry metrics

- Status: Accepted
- Date: 2026-07-28

## Context

Argus v2 needs a durable, self-hosted Prometheus-compatible store for passive
OpenTelemetry RED metrics. MySQL remains the control-plane database and the
low-cardinality OTLP receiver ledger; it must not become a high-volume
time-series store. The deployment model in this repository is a small Docker
Compose installation with MySQL and Redis. There is no evidence that warrants
Kafka or a distributed metrics cluster.

## Decision

Run pinned `victoriametrics/victoria-metrics:v1.148.0` as a single-node service
in `docker-compose.yml`.

- Store data in the durable `victoriametrics_data` named volume.
- Retain samples for 30 days with `-retentionPeriod=30d`.
- Reserve headroom with `-memory.allowedPercent=60`, a Docker `1g` memory cap,
  and `-storage.minFreeDiskSpaceBytes=5GB`; the latter makes the store stop
  accepting writes before the filesystem is exhausted.
- Use the Prometheus-compatible read API at
  `http://victoriametrics:8428/prometheus/api/v1` from the Argus Compose
  network. The development port is bound only to `127.0.0.1`.
- Health-check `http://127.0.0.1:8428/-/healthy` in Compose. The operational
  metrics endpoint is `/metrics`.
- Treat VictoriaMetrics as an internal dependency. Never expose its query or
  administrative API publicly; Argus applies project scope before issuing any
  query and prevents user-controlled PromQL.

VictoriaMetrics' official documentation recommends the single-node edition for
ingestion rates below one million data points per second, which fits the
repository's current deployment scale. Its official quick-start documents the
Docker image and storage path, while its retention guidance documents the
`-retentionPeriod` behavior. Review the pinned version during every planned
dependency update.

## Backup and restore

The named volume is durable across ordinary `docker compose down` operations.
Do not use `docker compose down --volumes` unless the metrics history is being
intentionally discarded.

For a consistent backup, create a VictoriaMetrics snapshot from the private
network, copy the returned snapshot directory from the volume to encrypted
object storage, and record the MySQL backup timestamp alongside it:

```bash
docker compose exec victoriametrics wget -qO- --post-data='' http://127.0.0.1:8428/snapshot/create
docker compose exec victoriametrics wget -qO- http://127.0.0.1:8428/snapshot/list
```

Restores are performed into a fresh stopped VictoriaMetrics volume according to
the upstream snapshot/restore procedure, then validated with a scoped Argus
metrics query and the store health endpoint. Practice this process before a
production cutover.

## Consequences

This adds one small, durable service and preserves a Prometheus-compatible
query surface for the SLO engine and UI. It is not a tenant boundary by itself:
all labels and every query must be generated by Argus after server-side project
authorization. If measured volume, availability, or isolation requirements
outgrow a single node, migrate to the documented VictoriaMetrics cluster
topology without changing the application-facing Prometheus API.
